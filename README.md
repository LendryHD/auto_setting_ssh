# Synet SSH Hardening

Скрипт автоматической настройки защиты SSH для Ubuntu Server 22.04, 24.04 и 26.04.

**Важно:** скрипт изменяет SSH-аутентификацию и порт. Перед запуском обеспечьте доступ к аварийной консоли VPS у провайдера и убедитесь, что у вас есть **приватный SSH-ключ**, соответствующий публичному ключу, который будете вводить.

## Установка одной командой

```bash
curl -fsSL https://raw.githubusercontent.com/LendryHD/auto_setting_ssh/main/synet-ssh-hardening.sh -o /tmp/synet-ssh-hardening.sh && sudo bash /tmp/synet-ssh-hardening.sh
```

Скрипт попросит ввести имя пользователя, пароль для `sudo` и **публичный** SSH-ключ в формате `ssh-ed25519 AAAA...`. Приватный ключ в скрипт вводить не нужно.

После этого он добавит/настроит пользователя, разрешит ему `sudo`, запишет публичный ключ в `authorized_keys`, запретит вход SSH под `root` и по паролю и выберет новый случайный порт. Если UFW активен, добавится разрешение для нового порта. Для Ubuntu с `ssh.socket` предусмотрена настройка порта сокета.

## Подтверждение нового подключения

**Не закрывайте текущую SSH-сессию.** После настройки старый SSH-порт временно остаётся доступным. Откройте вторую SSH-сессию по новому порту с подходящим приватным ключом:

```bash
ssh -p НОВЫЙ_ПОРТ -i /путь/к/приватному_ключу пользователь@IP_СЕРВЕРА
```

В новой SSH-сессии выполните **без изменения синтаксиса**:

```bash
sudo env SYNET_CONNECTED_PORT="${SSH_CONNECTION##* }" /usr/local/sbin/synet-ssh-guard --confirm
```

После подтверждения скрипт попытается отключить старые SSH-порты. Если подтверждение не поступит в течение 15 минут, systemd-таймер попытается восстановить предыдущие настройки SSH. Настройки пользователя/пароля/ключа при откате не удаляются. Если systemd или сеть работает неправильно, может потребоваться восстановление через консоль провайдера.

Внешний файрвол хостинга скрипт **не настраивает**. Разрешите в нём новый TCP-порт до проверки. Правила старого порта в UFW автоматически не удаляются, поскольку могут использоваться другими сервисами.

## Безопасность

- Для продакшена лучше использовать проверенный commit SHA вместо постоянно обновляемой ветки `main`.
- Скрипт не проходил полноценного тестирования на реальном VPS; сначала протестируйте на тестовой машине.
- Смена порта сама по себе не заменяет SSH-ключи, ограничения доступа и корректный файрвол.
- Автоматизация (например, eGames) и SSH-клиенты должны быть перенастроены на нового пользователя и порт.
